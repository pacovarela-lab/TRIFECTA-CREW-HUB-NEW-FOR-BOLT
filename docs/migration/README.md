## Frontend environment and Auth

`vite.config.ts` no longer injects a production URL/key or reads server-variable fallbacks. Each host supplies `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` at build time. `.env.example` has empty placeholders. Missing/invalid configuration displays a controlled Spanish message before loading the app or constructing the client. Backend/service-role credentials are never frontend configuration.

The Google button now invokes the existing Supabase client's `signInWithOAuth`. It returns to the same origin's `/login`; a restored session follows the existing route to `/`. Cancellation/error callbacks display a generic Spanish error and remove provider error parameters. Password login, `AuthContext`, profile/company membership checks and protected-route enforcement are unchanged.

The SDK's normal browser storage replaces the preview editor broker. Tests using the real locked SDK with mocked network verify the existing storage key is restored, logout clears it, and OAuth URL tokens become a persisted session and are removed from the URL. The Lovable integration and preview storage file are now unused and removed, along with `@lovable.dev/cloud-auth-js`. The lockfile loses exactly that one package entry, with zero additions or changed retained entries.

## Controlled reconstruction and copy protocol

1. Require an explicitly approved owner-controlled target ref. Reject the current source and both prohibited refs. Verify account ownership and connection identity before every write operation; do not use a default CLI link or a guessed project.
2. Obtain read-only source catalog/account inventory and compare it to the Git manifest. Back up source with supported export facilities into encrypted restricted storage outside Git. Record source snapshot identity/time, migration history and file/chunk checksums.
3. Rehearse schema replay on an isolated target, stop on any error and inspect the effective schema. Control source-directed triggers, cron, email/SMS and other outbound effects before loading data. Resolve missing managed email components. No edits to source production.
4. Plan Auth user/identity import through supported Supabase methods preserving user UUIDs and confirmation state. Do not invent password hashes. Verify target signup triggers cannot create duplicate profiles or companies during import. Existing sessions reauthenticate after switching projects.
5. Derive final table ordering from live `pg_constraint`, including private and Auth schemas. Resolve FK cycles explicitly through supported deferrable constraints or reviewed two-pass nullable references on the target; never globally disable security to make a copy pass.
6. Copy in deterministic primary-key chunks, preserving `company_id`, foreign keys, timestamps, exact numerics and all Estimate Photo records. Track per-chunk checksums, counts and completion checkpoints. A retry may skip an identical existing row; a different row with the same key is a stop condition, not an overwrite. Classify generated/seed rows before combining them with exports.
7. Restore sequences/identity state from verified catalogs and check that next values exceed copied maxima. Prevent `updated_at` triggers from rewriting historical timestamps using a narrowly scoped target-only import strategy. Restore and verify every affected trigger afterward. Do not replay historical notification deliveries.
8. Copy Storage bytes through the supported API with unchanged paths/tenant ownership/content types. Compare object counts, lengths and SHA-256 hashes; metadata-only copying is not object migration. Audit persisted source URLs and generate target signed URLs without modifying financial history.
9. Compare exact counts and canonical row hashes for every copied tenant/table, plus all financial aggregates. `financial-readonly.sql` provides initial exact numeric checks, including null/unassigned groups; it is not sufficient by itself. Extend checks from the live catalog to bank transactions, splits, V10 controls, estimates and each recorded currency. Verify `worker_checkins` keys/timestamps exactly and the ledger view's underlying records. Any nonzero delta blocks cutover; never round away a difference or alter legitimate records.
10. Run cross-tenant reads/writes with at least two authenticated non-service-role test identities; prove table/RPC/Storage policies, roles, trial gates and Approved-estimate immutability. Run Auth sign-in/sign-out/restore and real Google callbacks, object download/upload, every Edge function and AI contract smoke on target. Estimate Photo must create no unintended writes in expenses, payments, worker_checkins or ledger sources.
11. Before final copy, freeze source business writes through an approved maintenance gate or implement and verify incremental catch-up. A pair of unrelated snapshots is not final reconciliation. Prove all gates and obtain the owner's explicit cutover approval before changing production frontend environment/DNS/traffic.

## Rollback plan (not executed)

Keep the source backend intact and retain the current frontend release and its environment snapshot in hosting secret storage. Keep source rollback access and database backups verified. Record source/target refs, release SHAs, build identifiers and restore procedure before requesting cutover approval.

If target smoke fails before switching traffic, do not cut over. Disable target outbound workers to prevent duplicate messages; preserve failed-target evidence for diagnosis. Source remains the active application.

If a fault occurs immediately after an approved cutover, pause writes first. If no target-only business writes exist, restore the prior frontend release and environment, verify Auth and financial state, then resume source operation. If target-only writes exist, do **not** blindly switch back: reconcile/export those writes with tenant-safe idempotency and exact financial verification, obtain the approved recovery decision, then restore service. Never delete or overwrite source records just to force rollback.
